# lingdiff
Tool for linguistic comparison between languages.

## Environment

**Depends on an external drive staying mounted**, same setup as the `ye_olde` project:
`/media/dahrs/My_passport` is too small on root (`/`) for Python envs/data, so:

- `.venv` -> `/media/dahrs/My_passport/lingdiff-venv`
- `data/sources/` (raw WALS/PHOIBLE/Glottolog/ASJP dumps + LLM cache, gitignored,
  regenerated by `pipeline/fetch_sources.py`) -> `/media/dahrs/My_passport/lingdiff-data-sources`
- `uv`'s package cache is also relocated machine-wide via `UV_CACHE_DIR` in `~/.bashrc`
  -> `/media/dahrs/My_passport/uv-cache`

If the drive isn't mounted, `uv run ...` and the pipeline scripts will fail outright.
`docs/data/*.json` (the small, committed outputs the website actually reads — see "Website"
below for why `docs/`, not top-level `data/`) lives in the repo as normal and doesn't depend
on the drive.

## Data pipeline

```
uv run python -m pipeline.run_pipeline
```

Downloads WALS (CLDF), PHOIBLE, and Glottolog source data into `data/sources/raw/` (cached —
reruns skip files already present), builds one `LanguageProfile` per leaf entity WALS has an
ISO 639-3 entry for (`WalsData.all_iso_codes()` — currently 2442 languages, the natural
ceiling since every leaf profile requires a WALS match) plus a handful of hardcoded
"group"-level family/macrolanguage entries (`_DRAFT_GROUP_ENTITIES` in `run_pipeline.py`), and
writes `docs/data/languages/<glottocode>.json` + `docs/data/index.json`.

**Runtime at this scale**: the dominant cost is Wikidata lookups — up to ~8 requests per
language (1 combined query for writing-system/case/tense/mood/aspect, ~2 for the family tree,
~3 for the Wikipedia-grounding title) even after combining 5 separate grammar-property
queries into 1 (see `wikidata_lookup.WikidataGrammarCache`). The public endpoint's reliability
varies a lot hour to hour (clean runs and sustained 502/timeout stretches both observed live
in the same session) — a full build can run anywhere from a couple hours to most of a day.
**Safe to interrupt and resume at any point**: every expensive lookup is cached in its own
file under `data/sources/raw/`, independent of the top-level loop, and a failed query is never
written to cache as if it were a confirmed empty result (see `wikidata_sparql.run_query`) —
so a rerun only pays real cost for languages that genuinely weren't cached yet.

**Two kinds of entity** (`LanguageProfile.comparison_kind`, see `pipeline/schema.py`):
- **`leaf`** — a single speakable variety (a language or a dialect — Glottolog's own
  `glottolog_level` label, not something that changes how it's built). Spanish, Levantine
  Arabic, and Standard Arabic are all `leaf`; Levantine/Egyptian Arabic are **siblings** of
  Standard Arabic under the Arabic macrolanguage, not dialects of it (confirmed against
  Glottolog's own classification) — this is what makes "Levantine Arabic vs. French" and
  "Levantine Arabic vs. Standard Arabic" both valid, independent comparisons.
- **`group`** — an aggregate node (a Glottolog family grouping, or an ISO 639-3 macrolanguage
  like Arabic) with *only* `classification` populated — there's no single phoneme inventory or
  word order for an entire family, so every other field stays empty. This is what makes
  "Levantine Arabic vs. Italic languages" a valid (if score-limited) comparison: family
  distance still works via the classification paths' common prefix, nothing else does.
  Built by `build_profile.build_group_profile`; for this draft the 3 example groups (Romance,
  Italic, Arabic) are hardcoded in `run_pipeline.py` rather than swept from Glottolog's full
  languoid table — scaling that up is future work, not yet needed for a small draft set.

Per **leaf** entity, each profile combines:
- **WALS** — genealogical path (Family/Subfamily/Genus, used as a fallback/sanity-check — see
  below), word-order features, tense/aspect/case-marking categories, writing system where
  coded (sparse), and now **all 192 WALS parameters** — anything not already captured by a
  more specific category above lands in `other_typological_features` (numeral classifiers,
  reduplication, politeness distinctions, etc.). **Caveat, found at full scale**: 928 of
  WALS's 3573 rows have an empty `Glottocode` column — 11 of them ISO-coded languages this
  pipeline actually builds, including Albanian. Since `glottocode` doubles as each profile's
  output filename, all 11 were silently colliding on the exact same file (`docs/data/
  languages/.json`), each overwriting the last — confirmed live, only the alphabetically-last
  of the 11 survived after a full build. `build_profile.py`'s `effective_glottocode` now
  falls back to a synthetic `iso-<code>` identifier (e.g. `iso-sqi` for Albanian) whenever
  WALS's own value is empty, which can never collide since `iso639_3` is already unique per
  profile. `pipeline/repair_empty_glottocodes.py` is the one-off script that fixed an
  already-built dataset without a full ~2442-language rerun (everything it needs is already
  cached — pure local recomputation).
- **PHOIBLE** — phoneme inventory (IPA symbols)
- **Glottolog** — real lat/lon + macroarea (context only, not used in any distance score) and
  `glottolog_level` ("language"/"dialect")
- **URIEL / lang2vec** — dense genetic/syntactic/phonological/inventory feature vectors (the
  `_knn` sets specifically — the only ones guaranteed to have no missing values; see
  `pipeline/uriel_vectors.py`). These, not the human-readable classification path below, are
  the actual basis for the genetic distance SCORE.
- **Wikidata** (`pipeline/wikidata_lookup.py`, `pipeline/wikidata_family_tree.py`; see
  `pipeline/wikidata_sparql.py` for the shared querying/caching/retry logic used by both):
  - *Writing system* fallback when WALS has none.
  - *Grammatical case/tense/mood/aspect* — real named enumerations (confirmed live: German's
    actual 4 cases, Finnish's ~15), not just a typological yes/no the way WALS's own
    case-related parameters are. **Caveat**: Wikidata's tagging isn't perfectly rigorous —
    confirmed live, Levantine Arabic's `grammatical_cases` includes "Iḍāfah", which is a
    possessive *construction*, not a case. Not filtered out automatically (no principled way
    to do that without linguistic authority over what counts) — flagged here for review
    instead.
  - *Deep family tree* — the real multi-level classification (e.g. "Spanish → Castilian →
    West Iberian → Iberian Romance → ... → Indo-European"), replacing WALS's shallow 3-level
    Family/Subfamily/Genus columns, via `P279` ("subclass of") edges filtered to nodes tagged
    "instance of: language family" (`Q25295`). **Caveat, with a safety net**: Wikidata
    sometimes encodes a disputed/alternative classification alongside the mainstream one
    (confirmed live: Mandarin's raw chain ending at "Dené–Caucasian" instead of Sino-Tibetan,
    Korean's at the contested "Altaic" hypothesis, French's at an areal "Southern European
    language" tag instead of Indo-European) — `build_profile._root_matches_wals_family`
    checks the climbed root against WALS's own top-level `Family` value and falls back to
    WALS's shallower-but-reliable path on any mismatch, rather than show a chain that might be
    wrong throughout. `Classification.path_source` records which one a given profile used.
    Separately, `build_profile._dedupe_consecutive` collapses same-name steps in a row —
    caught two different ways this happens: Japanese's raw Wikidata chain repeated
    "Japanese" three times (different entities sharing one English label, which the
    tree-walk's cycle guard — keyed on entity ID, not label — doesn't catch), and WALS's own
    data for Japanese has Family/Genus/Name all literally "Japanese" too.
- **LLM enrichment** (`pipeline/enrich_llm.py`) — a short grounded "notable features" blurb,
  plus writing-system classification as the last-resort fallback when WALS, Wikidata, *and*
  this both have nothing. Grounded in a fetched Wikipedia extract (via the language's Wikidata
  sitelink) + the structured facts already gathered — never left to the model's unaided
  memory — and skipped entirely (not called) when no Wikipedia article was found to ground it
  in. Calls go through **`claude -p` (the CLI)**, not a hosted `ANTHROPIC_API_KEY` — see
  `pipeline/claude_cli_client.py` (same approach as ye_olde's `common/claude_cli_client.py`,
  reusing a `claude login`'d subscription session instead of pay-per-token billing). Requires
  `claude` on PATH and logged in.

**Caching**: every external lookup (Wikidata of all kinds, Wikipedia, LLM) is cached to its
own file under `data/sources/raw/`, and — important — a *failed* query (the public Wikidata
endpoint does time out under load) is never written to cache as if it were a confirmed empty
result; it's simply retried fresh on the next pipeline run. See `pipeline/wikidata_sparql.py`.

Currently covers a small draft set (~26 leaf entities + 3 group entities) to get something
reviewable before scaling up — see "To do" below for what's intentionally deferred. No LLM
calls happen at site runtime — this is an offline, one-time-per-entity data-build step only.

**Dependency note**: `lang2vec` imports the deprecated `pkg_resources`, which `setuptools>=81`
dropped — `pyproject.toml` pins `setuptools<81` to keep it working.

## Website

`docs/` is a plain static site (HTML/CSS/vanilla JS, no build step, no framework) — GitHub
Pages serves a repo's chosen folder directly, which is *why* the pipeline writes its output to
`docs/data/` rather than a top-level `data/`: anything outside the published folder simply
isn't reachable once Pages is enabled, regardless of relative-path tricks.

- `index.html` / `styles.css` — layout
- `compare.js` — pure comparison functions. Each category's score is `null` (not a fake
  maximal-distance value) whenever either side is simply missing data for it — see
  `diffSets`'s docstring; conflating "no data" with "confirmed zero" was a real bug caught in
  review (Levantine Arabic has no PHOIBLE phoneme entry, which was scoring it as 100%
  phonologically different from everything, dragging every comparison involving it toward
  "very distant" regardless of actual relatedness). Family distance matches on the **deepest
  shared name anywhere in both classification paths**, not a positional common *prefix* —
  needed because two entries can have same-family paths of different depth depending on
  whether they got Wikidata's deep chain or WALS's shallower fallback (confirmed live:
  Levantine vs. Egyptian Arabic, both genuinely close Semitic languages, scored as nearly
  unrelated under prefix-matching because Egyptian Arabic's WALS-fallback path has no
  separate "Arabic" step at all — it jumps straight from "Semitic" to the specific variety).
- `languagePicker.js` — the picker itself: a custom listbox (not a native `<select>`, which
  can't reliably style `<option>` font-weight/indentation across browsers) that **nests each
  language under its macrolanguage/family** rather than listing everything alphabetically
  flat. Matches on word-boundaries within path elements, not exact position or plain
  substring (plain substring wrongly nests German's Germanic siblings *under* German itself,
  since "german" is a literal substring of "Germanic languages" — word-boundary matching
  requires "german" to be a whole word in some element, which it isn't there, but "Arabic" is
  a whole word in "Arabic (Egyptian)"). Falls back to checking the entry's own leaf name only
  when nothing at all matched further up its ancestor chain, for sources sparse enough to
  skip a level entirely (same Egyptian Arabic case as above). Its panel also opens with a
  type-to-search box, auto-focused — scrolling ~2400 entries by hand wasn't practical once
  broad coverage landed. Matches by word-prefix (typing "Beirut" finds "Arabic (Beirut)", not
  just names literally starting with it) against the name or the ISO 639-3 code; Enter
  selects the first visible match, Escape closes.
- `diffView.js` — the reusable "shared / only-in-A / only-in-B" renderer behind the
  public-friendly requirement (phonemes, grammatical categories, writing-system scripts, etc.
  all reduce to this)
- `summary.js` — template-based narrative over the already-computed facts
- `app.js` — fetches `data/index.json` once + the two selected profiles lazily; each category
  section is a native `<details>`/`<summary>` (click the title to expand/collapse, no custom
  JS needed for that) with its own 0–100 score badge next to the title, same scale as the
  overall score (an explanatory line under the overall number spells out what it means — "0
  = identical, 100 = maximally different" — since an unexplained number was flagged as
  confusing in review). Also renders the closest/farthest panel (below) as soon as language A
  is picked — no fetch, since that data already rode along in `index.json`.

**Closest/farthest-in-the-list panel**: picking language A immediately shows a **top-3
gold/silver/bronze podium** — the 3 closest and 3 farthest other leaf languages in the whole
dataset, independent of whatever's picked for B (clicking any entry loads that exact pairing
into the full comparison below; rank 1 is the full card, ranks 2-3 collapse to a smaller
one-line button). This can't be computed live in the browser the way the main comparison
is — finding "closest among all ~2400 languages" means comparing every pair, which would mean
either downloading every profile into the browser (defeats the lazy-fetch design entirely) or
redoing an O(n²) pass on every single pickerA change. Instead it's precomputed once, offline,
in the pipeline (`pipeline/scoring.py` + `pipeline/nearest_neighbors.py`) and shipped as plain
data on each `LanguageIndexEntry` (`closest`/`farthest`, each a list of up to 3
`schema.NearestNeighbor`s, best first) — the picker already has the whole index loaded, so
showing it costs nothing extra at view time. Restricted to `comparison_kind="leaf"` entries
only on both sides: comparing against a "group" (family/macrolanguage) entity has far fewer
scoreable categories, which would make group entities spuriously dominate "farthest" for
nearly everyone — "closest *language*" should mean closest among actual languages, not among
the small set of hand-picked families.

**Modality-aware (sign vs. spoken)**: every leaf profile has `is_sign_language`
(`schema.LanguageProfile`/`LanguageIndexEntry`), detected primarily from WALS's own
`Genus == "Sign Languages"` (covers all 40 WALS-listed sign languages precisely — confirmed
live, only 26 of the 40 have "sign" literally in the name, e.g. "Auslan", "Deutsche
Gebärdensprache", "Lengua de Señas Argentina" don't), with a name-keyword fallback
(`build_profile.is_sign_language_for`) for any entity built without a WALS row. The podium
computation (`nearest_neighbors.py`) skips offering a candidate to either side when the two
profiles disagree on `is_sign_language` — visual-gestural vs. spoken modality swamps every
other typological signal this tool scores, and without this guard a sign language's "closest"
podium would tend to fill up with spoken languages that simply have sparse/absent phonology
data (scored as incomparable, never as maximally distant — see the missing-data-safety point
above), which is a meaningless comparison in either direction. Backfilled onto the full
already-built dataset via `pipeline/backfill_sign_language.py` (local-only, no network calls —
same pattern as `repair_empty_glottocodes.py`); verified live that every one of the 40 sign
languages' closest/farthest podiums contain only other sign languages, and spot-checked spoken
languages (e.g. Spanish) show none.

**Sign languages used to all score identically against each other — fixed, with two real
gaps closed**: every pairing lacking both writing-system AND word-order data (the overwhelming
majority) fell back to family distance alone, and that was *also* broken for sign languages
specifically. The actual bug: WALS's own "Family" column is the literal placeholder `"other"`
for every one of its 40 Sign Languages genus rows — it was never intended to carry a real
top-level family for this genus — but `_build_classification`'s trust check
(`_root_matches_wals_family`) didn't know that, so it rejected Wikidata's real, specific
sign-language genealogies (e.g. "BANZSL" uniting British/Australian/NZ Sign Language, a
"French Sign Language family" uniting French/American/Quebec Sign Language — already being
fetched and cached, just discarded) every time, because they obviously never matched the
placeholder "other". Every sign language fell back to the same flat
`["other", "Sign Languages", <name>]` WALS-only path, making family distance — and therefore
the whole score, for any pair without the rare writing-system/word-order data below — come out
identical for nearly every pairing (confirmed live: 33, unconditionally). Fixed: WALS's
"other" is now treated as "nothing to validate against" **specifically for the Sign Languages
genus** (unlike Creoles and Pidgins, which also code `Family="other"`, but deliberately — a
creole genuinely has no single lineage to check a root against, so that case is left alone).

Second gap, newly sourced: WALS's Ch.81 (basic word order) has no parameters at all for sign
languages, but Wikidata's P4132 ("linguistic typology") property does give a real SVO/SOV/
OSV-style value for some of them — confirmed live, 5 of the 40 (ASL "subject–verb–object",
British Sign Language "object–subject–verb", German Sign Language "subject–object–verb",
Quebec Sign Language and Italian Sign Language also covered). `wikidata_lookup.py` now fetches
this alongside its other 5 properties; `build_profile.py`'s `_normalize_word_order_label`
converts Wikidata's spelled-out label to WALS's own SVO-style abbreviation so the two sources
are directly comparable, and feeds it into `syntax.features` like any other word-order
feature — appears for every language, filled only where a source actually has it (sign or
spoken), exactly the "same field, sparse outside sign languages" shape vocabulary origin and
sample_glyphs already use.

Both fixes are scoped to the 40 sign languages specifically (`pipeline/
backfill_sign_language_typology.py` — re-fetches just their Wikidata grammar data via a new
`WikidataGrammarCache.invalidate()`, since a plain cache hit wouldn't have picked up the new
P4132 property, then rebuilds their profiles and recomputes `index.json`'s podiums from the
complete set). Verified live, and linguistically sensible: ASL's closest match is now Quebec
Sign Language (a direct, documented descendant, score 15 — "very close"), and British Sign
Language's/Auslan's closest matches are each other plus New Zealand Sign Language (all three
really do belong to the BANZSL family) — none of which could be expressed before this fix.

`pipeline/scoring.py` is a **hand-maintained Python port** of `compare.js`'s overall-score
math (no Node/JS runtime available in this environment to run the real JS from Python, and no
shared implementation between the two — see that file's docstring). If you change the scoring
in one, change it in the other; verified live that they produce matching results on the same
data (French↔Italian, Spanish↔Portuguese, German↔Dutch, and both Arabic-dialect pairs all come
out as each other's closest match, as expected), but there's no automated check enforcing
that the two stay in sync going forward.

**Family-distance bug, fixed**: `compareFamily`/`_family_distance` used to score two languages
with ZERO shared classification-path ancestor as something less than maximally distant
whenever their paths had different lengths (common — one side's path can come from a deep
Wikidata chain, the other from WALS's shallower 3-level fallback) — the old
`(hopsA + hopsB) / (2 * maxDepth)` formula let the shorter path's length alone pull the score
down, even with no real relatedness at all. Confirmed live: a pair sharing no family node
whatsoever (e.g. Bachamal, path length 2, vs. Sora, path length 4) scored "distant" instead of
"very distant". Now: no shared ancestor anywhere in either path means score = 1 (100), full
stop, unconditionally — recomputed across the whole dataset (`index.json`'s podiums changed;
no profile files did, confirming this was scoring-only).

A language can genuinely use more than one script at once (`WritingSystem.scripts` is a
list, not a single name) — Japanese routinely uses 4 (hiragana/katakana/kanji/kana), and
several Arabic varieties are tagged with the Arabic script *and* an informal Latin-based
"chat alphabet"/romanization. Compared the same way as phonemes (shared/only-A/only-B over
script names), falling back to a looser "at least the same script *type*" match when no exact
script name is shared. Script-type detection (`wikidata_lookup.script_type_for`) matches on
the script *family* name as a substring (Wikidata labels the same family inconsistently as
"<Family> script" vs. "<Family> alphabet" — confirmed live, Levantine vs. Egyptian Arabic), with
one explicit carve-out: a "chat alphabet" (Arabizi-style informal romanization) is Latin-based
by definition, not the family's native script, so it's checked before the general match. A
further fallback, also fixed: Wikidata often names a language's own Latin-based alphabet after
the LANGUAGE rather than the script family (confirmed live: "French alphabet", "Italian
alphabet", "German alphabet" — no family-name substring matches "french"/"italian"/"german"),
which used to fall all the way to the generic "other" type despite the name saying "alphabet"
outright; now defaults to "alphabet" whenever the name says so and isn't a Braille entry.

**Letter-level writing-system comparison (Unicode CLDR), added**: name/type matching alone
couldn't express that French's and Italian's alphabets, despite being named completely
differently ("French alphabet" vs. "Italian alphabet" — zero name overlap), are actually
almost entirely the same set of letters. `pipeline/cldr_loader.py` parses Unicode CLDR's
per-locale "exemplar character" data (`pipeline/fetch_cldr_sources.py` downloads it; a real
structured source, not an LLM guess — the same data other software uses for "what letters
does this locale's orthography use") into `Script.sample_glyphs`, attached by
`build_profile.py`'s `attach_sample_glyphs` to whichever ONE of a profile's script entries is
its unambiguous primary, non-Braille script (skipped entirely for multi-script profiles like
Japanese's 4 scripts — CLDR's locale-level data doesn't say which script it belongs to, so
it's never guessed onto any one of them). `compareWritingSystem`/`_writing_system_distance`
use this letter-by-letter overlap as the score whenever both sides have it, falling back to
the name/type match otherwise; `app.js` renders it as its own shared/only-A/only-B grid above
the named-script one. Verified live: French vs. Italian share 30 of their letters, with only
12 (French) + 2 (Italian) differing — accented/ligature characters, not a different alphabet —
giving a 32% writing-system distance instead of the old all-or-nothing name match.
Coverage is partial by nature of the source: CLDR only has ~250 single-script "base" locales
(no region variant, no script-disambiguated macrolanguage like "zh-Hans"/"sr-Cyrl" — those are
downloaded but deliberately left unmatched, see `cldr_loader.py`'s docstring), so only 122 of
2444 profiles got letter data on this pass. Backfilled onto the already-built dataset via
`pipeline/backfill_sample_glyphs.py` (fetches CLDR once, re-derives every script's type with
the corrected fallback above, then recomputes `index.json`'s podiums with the new scoring) —
`build_profile.py`'s own `cldr` parameter means a future full `run_pipeline.py` run gathers
this from the start, same pattern as vocabulary origin.

No LLM call anywhere in `docs/` — everything there is arithmetic/set-logic over already-fetched
JSON, per the project's core design constraint.

**Not yet verified in an actual browser** — this sandboxed environment has no browser or JS
runtime available, so this was checked by serving `docs/` locally and confirming the data/JS
files are reachable (`curl`), a manual code read-through, a brace/paren balance check, and a
from-scratch Python reimplementation of the comparison/picker-nesting logic run against the
real data to confirm the actual math and tree structure, not just that the JS parses. Please
open the real page yourself before trusting it works end-to-end — a logic re-implementation
confirms the algorithm, not that the DOM renders it correctly.

## Vocabulary origin

`LanguageProfile.vocabulary_origin` (see `schema.VocabularyOrigin`) — an estimated
borrowed-vs-inherited ratio plus a donor-language breakdown ("37.8% from Latin, 11.6% from
French, ..."), not just a single number. Two sources, WOLD preferred:

- **WOLD** (World Loanword Database, `pipeline/wold_loader.py`) — expert-curated, 41
  languages. Gives a *graded* `Borrowed_score` per word (0.0-1.0, not binary) and the actual
  donor language **by Glottolog code**, not just a name — both richer than what was first
  scoped for this ("just a ratio would work").
- **etymology-db** (`pipeline/etymology_db_loader.py`) — a dataset auto-parsed from
  Wiktionary's own etymology templates, CC BY-SA 3.0, covering 3300+ languages/dialects at
  very uneven depth. Fallback for whatever WOLD doesn't cover. Its real distribution channel
  (a GitHub README's OneDrive link) doesn't support plain HTTP download — confirmed live,
  redirects to onedrive.live.com and 403s a non-browser request — so this pulls the
  community-maintained Hugging Face mirror instead (`Nickmancol/etymology`, same license,
  same data, ordinary HTTPS). Donor languages here are free-text names (e.g. "Ancient
  Greek"), not codes; `pipeline/iso_language_codes.py` maps those (and etymology-db's own
  `lang` column) to ISO 639-3 using Wiktionary's own code table plus SIL's official ISO 639-1
  <-> 639-3 equivalence — confirmed live that ~7400 of Wiktionary's ~8600 codes are already
  bare ISO 639-3 (its 2-letter codes are the ones needing a lookup, and are exactly the major
  world languages: English, French, German, Spanish, Arabic, Chinese, ...).

**Why WOLD is preferred, not just listed first — a real, confirmed-live finding, not a
theoretical concern**: etymology-db gives Mandarin Chinese an 86% borrowed ratio (dominated
by English/Japanese donors); WOLD's expert-curated score for the same language is 2%. This
isn't noise, it's systematic: Wiktionary's etymology templates get applied far more
consistently to loanwords (which editors find interesting to document) than to a language's
inherited core vocabulary — especially for a language in a non-Latin, non-alphabetic script.
Arabic shows the same pattern (84.7% from etymology-db) and WOLD doesn't cover it at all, so
that number should be treated with real skepticism rather than as a measurement — flagged in
code and here, not silently corrected (there's no principled way to correct it without an
independent, reliable second source, which is exactly what WOLD is where it's available).
`VocabularyOrigin.source` and `.sample_size` are on every entry specifically so this kind of
reliability difference is visible, not hidden behind one flat ratio.

**Surfaced in the website** as its own collapsible section (`compare.js`'s
`compareVocabularyOrigin` + `app.js`'s `renderVocabularyOriginSection`): each language's own
borrowed-vocabulary percentage/sample size/source, plus a shared/only-in-A/only-in-B diff
over donor-language names (the same pattern phonemes and scripts use). That donor-overlap
score is shown in the section's badge but, as planned, deliberately **excluded from the
overall distance score** — it's informational (donor-language/contact history), not a
structural-similarity measure; two languages can share an identical borrowing history while
being typologically nothing alike, or vice versa, so folding it into "how close are these
languages" would conflate two different questions.

**Donor-overlap bug, fixed**: a language never lists itself as its own donor (why would it?),
but when comparing A to B where B was *directly* influenced by A, A's name should still land
in the shared column — it's not some unrelated third language that coincidentally matches,
it's literally the other side of this very comparison. The plain set-diff over donor-language
names couldn't express that: confirmed live, comparing Italian to Dullay (Gollango) — whose
donor list includes "Italian" — showed "Italian" as only-in-Dullay's set, not shared.
`compareVocabularyOrigin` now checks, before diffing, whether either side directly donated to
the other, and folds that name into the shared set when so; verified against the same
Italian/Dullay pair.

**Backfilled separately from the main pipeline, by design** — see
`pipeline/backfill_vocabulary_origin.py`'s own docstring for why: it was built and run
*while* the 2442-language full build was already in progress (see "Data pipeline" above), to
avoid interrupting a run that was already taking the better part of a day. It only touches
the `vocabulary_origin` field of already-written profiles — confirmed live, safe to run
concurrently with `run_pipeline.py` (no file either process touches is written by both in the
same run) and idempotent to rerun. `build_profile.py`'s own `VocabularySources` plumbing means
a *future* full `run_pipeline.py` run gathers this from the start like everything else; the
backfill script is only needed for profiles built before that existed, or after interrupting
a run that predates it.
